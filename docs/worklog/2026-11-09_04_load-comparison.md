# 작업 기록 04: 수정 전후 200건 부하 비교

- **일자:** 2026-11-09
- **담당:** 허재원
- **요청:** 중단되었던 부하 비교 진행
- **코드 변경:** 없음. 이 문서 추가, 작업 기록 03의 관련 항목 갱신
- **대상:** 작업 기록 03의 수정 전 코드(OLD)와 수정 후 코드(NEW)

## 1. 방법

- `tests/test_stress_load.py`로 200건을 순차 요청했다 (히트맵 포함, `SAFETY_FIRST`).
- 순서 편향을 줄이려고 OLD, NEW, NEW, OLD 순으로 실행했다.
- 임시 복사본에서 Python 3.13으로 실행했고, 실행한 코드가 프로젝트의 `server.py`, `audit_logger.py`와 같은지 해시로 확인했다.
- `scratch` 이미지가 없어 `color` 이미지 복사본으로 대체했다. 판정 분포가 문서 값(PASS 69, REWORK 52, SCRAP 79)과 조금 다른 이유다.

## 3. 해석

- **기능 회귀 없음:** 오류 0건, 감사 로그 200행 증가, 판정 분포 동일, 메모리 증가 없음.
- **성능 차이는 판단 보류:** 같은 코드의 회차 간 평균 차이가 OLD 23.4ms, NEW 22.7ms로, 두 코드의 차이 12.6ms보다 크다.
- **P95 차이는 한 회차의 영향이 크다:** NEW 1회차만 390ms이고 2회차는 OLD 2회차보다 낮다. 다만 2회 측정으로는 우연이라고 단정할 수 없다.
- **제품 영향:** 가장 느린 요청도 546ms로, 대시보드 타임아웃 5초보다 충분히 짧다.

## 4. 한계

- 순차 요청만 측정했다. 수정의 핵심인 동시 요청 상황은 작업 기록 03의 별도 측정(8건 동시 1.70초)뿐이다.
- 200건씩 2회의 단기 측정이다. 장시간 가동 안정성은 검증하지 않았다.
- 로컬 루프백 환경이며, `fsync` 비용은 저장 장치에 따라 달라진다.
- `scratch` 대체 데이터를 사용해 공식 지표로 쓸 수 없다.

## 5. 함께 확인한 사항

role_2와 role_3의 공용 파일 11개(`server.py`, `audit_logger.py`, `rule_engine.py`, `patchcore_engine.py`, 테스트 3개, 메타데이터, 모델, `api.md`, `evaluation.json`)는 해시가 모두 같다.

- **전종현 (PM):** 현재 코드의 공식 부하 수치가 필요하면 실제 `scratch` 데이터를 확보한 뒤 다시 측정해야 한다. 그 전까지 기존 수치(평균 277ms, P95 332ms)는 수정 전 코드의 측정값으로 표기한다.
