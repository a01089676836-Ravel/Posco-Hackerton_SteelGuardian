## 📌 Q1. "비지도 학습인데 조도나 카메라 각도가 조금만 바뀌어도 오작동하지 않습니까?"
- **심사위원 의도:** 실제 제철 공장의 분진, 조명 변화, 진동 환경에서 2D 패치 기반 이상탐지의 취약점을 지적하려는 질문.
- **모범 답변:**
  > "매우 정곡을 찌르는 질문이십니다. 실제로 저희는 이 문제를 검증하기 위해 **조도 변화(±10%), 회전(±2°), 노이즈, 압축 등 7대 악조건 805회 스트레스 테스트**를 선제적으로 수행했습니다.  
  > 
  > 실측 결과, 치명 결함인 bent와 flip 44장은 어떠한 섭동 속에서도 100% SCRAP으로 안정 유지되었습니다.  
  > 다만, 원본 점수가 임계치 바로 위(0.6013)에 있던 `color/004.png` 샘플의 경우 조도 10% 감소나 회전 시 PASS로 판정 전환되는 2D 비지도의 물리적 한계를 정직하게 확인했습니다.  
  > 
  > 저희는 이를 숨기지 않고 두 가지 방식으로 해결했습니다.  
  > 첫째, 공정 규칙 엔진에서 경계 점수 구간은 사람의 2차 검증 큐로 분기하는 **`HUMAN_IN_THE_LOOP` 모드**를 지원합니다.  
  > 둘째, 하드웨어적으로 외란을 차단할 수 있도록 **차광 챔버(Light-shielding chamber)와 센터링 가이드 지그**를 표준 양산 사양으로 채택하도록 설계했습니다."

## 📌 Q2. "CPU에서 103ms라고 했는데, 실시간 라인에서 병목은 없습니까? (풀 트랜잭션 지연시간)"
- **심사위원 의도:** 순수 모델 추론 시간 외에 이미지 디코딩, 네트워크 통신, 히트맵 렌더링, DB 로깅이 포함된 실제 E2E 지연시간 확인.
- **모범 답변:**
  > "정확한 지적이십니다. 발표에서 말씀드린 **103.4ms(P95 112.5ms)**는 순수 알고리즘 추론 시간입니다.  
  > 
  > 실제 현장 운영 환경에서 네트워크 전송, 히트맵 Base64 인코딩, MES CSV 파일 락킹까지 포함된 **풀-트랜잭션 지연시간은 200건 스트레스 테스트 기준 평균 277.2ms(P95 331.9ms)**입니다.  
  > 
  > 포스코 부품 가공 라인의 이송 주기(Takt Time)는 부품당 약 1.5초에서 3.0초 수준입니다. 따라서 풀 트랜잭션 277ms는 공정 사이클 타임 대비 충분한 여유 마진(Safety Margin)을 가지며, 라인 병목을 유발하지 않습니다."

## 📌 Q3. "30초 만에 새 부품을 온보딩한다는데, 정상 이미지 20장만으로 모델 신뢰성이 나옵니까?"
- **심사위원 의도:** 소표본(Few-shot) 학습 시 과적합(Overfitting) 및 오탐/미탐 리스크 검증.
- **모범 답변:**
  > "통계적으로 소표본은 분산 추정의 불확실성이 필연적으로 발생합니다. 저희는 이를 방지하기 위해 **운영 신뢰도 등급(Confidence Tier) 시스템**을 탑재했습니다.  
  > 
  > 투입된 정상 이미지가 20~29장일 때는 시스템이 자동으로 `PILOT_LOW_CONFIDENCE` 등급을 부여하고, **자동 양산 승인을 원천 차단(`autonomous_decision_allowed=False`)**합니다. 대신 모든 경계 판정을 **수동 검토(MANUAL_REVIEW)**로 강제 분기합니다.  
  > 
  > 실측 결과 정상 이미지 30장 이상 확보 시 `PILOT` 등급, 100장 이상 확보 시 `STANDARD`, 190장 이상 전수 투입 시 `PRODUCTION_READY`로 등급이 격상됩니다. 따라서 30초 온보딩은 긴급 파일럿 라인 투입을 위한 안전 장치이며, 양산 무결성을 훼손하지 않습니다."

## 📌 Q4. "Anomalib 같은 오픈소스 프레임워크를 그대로 갖다 쓴 것 아닙니까?"
- **심사위원 의도:** 오픈소스 래퍼(Wrapper) 수준의 개발인지, 핵심 알고리즘 및 시스템 레벨 기여가 있는지 확인.
- **모범 답변:**
  > "저희 시스템은 **Anomalib을 전혀 사용하지 않고 순수 PyTorch로 자체 구현**했습니다.  
  > 
  > Anomalib은 무겁고 외부 의존성이 많아 공장 폐쇄망이나 CPU 임베디드 PC에서 구동하기 어렵습니다.  
  > 저희는 PatchCore 원논문(CVPR 2022)의 6번 식(최대 1-NN 거리)과 7번 식(근방 9개 메모리 밀도 재가중)을 직접 수식화하여 코어 엔진을 경량화했습니다.  
  > 나아가 단순 이상탐지를 넘어 **3-Tier 공정 의사결정 규칙 엔진, 원자적 모델 핫스왑, 멀티프로세스 동시성 파일 락, 100% 오프라인 Wheelhouse 패키징**까지 공장 운영 전반의 시스템 엔지니어링을 독자 완성했습니다."

## 📌 Q5. "공장 인터넷이 안 되는 환경(망분리)에서 실제로 진짜 돌아갑니까?"
- **심사위원 의도:** 외부 CDN, 클라우드 API, 텔레메트리 호출 등으로 인한 오프라인 먹통 가능성 확인.
- **모범 답변:**
  > "네, 100% 자립 구동됩니다. 저희는 이를 위해 세 가지 오프라인 방어 설계를 완료했습니다.  
  > 
  > 첫째, 백본 가중치(`resnet18_imagenet_v1.pth`)와 Coreset 모델을 로컬에 내장하고, 로드 시 `weights_only=True` 보안 검증을 거칩니다.  
  > 둘째, Streamlit 대시보드의 외부 텔레메트리를 차단(`gatherUsageStats = false`)하고, 외부 웹폰트나 CDN 의존성을 0건으로 제거했습니다.  
  > 셋째, Python의 `socket` 계층에서 `127.0.0.1` 루프백 외 **모든 외부 인터넷과 DNS 질의를 강제 차단한 상태에서 추론 및 대시보드 검증(`tests/test_offline_airgap.py`)을 전수 통과**했습니다.  
  > 패키지 설치 역시 103개 C 확장 wheelhouse를 동봉하여 오프라인에서 즉시 설치됩니다."

## 📌 Q6. "여러 규격의 부품이 동시에 들어오는 다품종 혼류 라인은 어떻게 지원합니까?"
- **심사위원 의도:** 단일 활성 모델 구조의 한계와 향후 시스템 확장성(Scalability) 검증.
- **모범 답변:**
  > "현재 해커톤 데모 버전은 단일 라인 단일 활성 모델을 기준으로 검증되었습니다.  
  > 하지만 저희는 다품종 혼류 생산 라인을 위한 확장 아키텍처 설계를 이미 완료하여 문서(`docs/MULTI_PART_LRU_CACHE_DESIGN.md`)로 공개했습니다.  
  > 
  > 핵심은 **Top-K 인메모리 `LRUModelCache`와 부품별 세분화 RLock**입니다.  
  > 검사 요청 시 `part_id`를 지정하면 메모리에서 가장 자주 쓰이는 모델을 즉시 호출하며, 서로 다른 부품 검사는 서로 다른 락을 사용하여 완전 병렬로 동시 추론됩니다. 메모리 초과 시 가장 오래 미사용된 모델만 안전하게 축출(Evict)하여 RAM OOM을 원천 방지합니다."

## 📌 Q7. "200건 스트레스 테스트는 했는데, 24시간 연속 가동해도 메모리 누수가 없습니까?"
- **심사위원 의도:** 장기 운영 시 가비지 컬렉션(GC) 실패 및 메모리 팽창 리스크 확인.
- **모범 답변:**
  > "로컬 200건 층화 연속 부하 테스트 결과, 초기 421.4MB에서 200건 완료 후 412.9MB로 오히려 8.5MB 감소하며 파이썬 가비지 컬렉션이 정상 동작함을 실측했습니다.  
  > 
  > 다만, 200건(약 1분) 테스트가 실제 제철소의 24시간 3교대 가동 전체를 대변하기에는 시간 규모의 한계가 있음을 솔직히 인정합니다.  
  > 따라서 해커톤 이후 실제 현장 도입 시에는 산업용 PoE 카메라와 연동하여 72시간 연속 내구 벤치마크 및 Prometheus 메모리 메트릭 수집을 후속 단계로 추진할 계획입니다."
